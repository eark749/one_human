    CHAPTER 1

    How One Human works

    In one lineEveryone online controls one single human together. Each person gets one body part.
    🏃

    Think of it likeA three-legged race with 34 people tied together, and nobody can talk. They can only point and shout single words.

    When you open the site you see the human standing in an empty room. Click Play and you get one body part, maybe the left leg. Your keys move only that leg. Other people have the other leg, the arms, the torso and the brain.

    The goal sounds easy: get the human to sit on the chair. But the two leg groups have to take turns, the torso has to keep balance, and nobody can talk properly. So the human falls over a lot. That is the game.

    Legs · 8 seats each · step to move
    Arms · 5 seats each · swing
    Torso · 6 seats · lean and balance
    Brain · 2 seats · sees the map, gives orders
    Objective · the chair

    The loop

    1Press Play
    2Get a body part
    3Work with strangers
    4Sit on the chair
    5Beat the record
    6Go again

    If the human hits its head too hard, everyone sees The human died. A new life starts with the next number. Every life is saved with how long it survived and how it died.

    These docs walk through the whole system, from what a player sends to how the body is simulated. Use the chapter list or the arrow keys.

    CHAPTER 3

    Server and client

    In one lineBrowsers only send wishes. One server decides what really happens to the body.
    ⚽

    Think of it likeA football referee. Players can shout "foul!", but only the referee decides.

    The client is the game in your browser. It reads your keys and draws the picture. The server runs the physics and holds the one true position of the body. This is an authoritative server.

    Clients never say "the leg is here". They only say "I want my leg to go forward". If clients decided positions, someone could send x = 999999 and the human would teleport. With an authoritative server, the worst a cheater can do is push their one leg a bit harder.

    They talk over a WebSocket: a connection that stays open so messages flow both ways many times a second.

    What the browser sends

    { "t": "in", "axis": 0.8, "up": false, "life": 7 }   // on every key change + every 250 ms
{ "t": "brain", "cmd": "WALK_RIGHT" }                // brain seats only
{ "t": "emote", "e": "GO" }

    CHAPTER 4

    The shared brain

    In one lineThe server averages everyone on the same body part, and that average moves the limb.
    🪢

    Think of it likeTug-of-war. 7 pull right and 3 pull left: the rope moves right, slowly. All 10 pull right: it moves fast.

    60 times a second, for each body part, the server adds up the axis of every active player and divides by how many there are. Results between −0.1 and +0.1 count as zero (the deadzone), so the limb doesn't shake from small random input.

    Try it. Each bar is one player. Up = forward, down = back. Click a bar to flip it, or load a scenario. (A real leg has 8 seats; the demo uses 24 to make the effect easy to see.)

    Left leg · 24 players
    Active24
    Average0.00
    Agreement0%
    Hip target0°
    for each body part:
  active = players heard from in the last 0.5 s
  mean   = sum(axis) / active.length
  if |mean| < 0.1: mean = 0                  // deadzone
  hip target = mean × 1.0 rad               // the motor moves the leg there

    Why an average and not a vote? A vote snaps between forward and back. An average is smooth, and players can see when they are fighting each other. Random noise cancels out, and trolls only make a limb weaker.

    Why only 34 seats. With 2,000 people on one leg, each person moves it 0.05% and random inputs cancel out. Nothing happens and nobody feels in control. So each part has a fixed number of seats (8 per leg, 5 per arm, 6 torso, 2 brains). Everyone else waits in line and gets the next free seat. The first players fill the legs, torso and brain first, so even three people can walk.
    CHAPTER 5

    The brain role

    In one lineBrains can see the chair but can't move the body. The body can move but can't see where to go.
    🚣

    Think of it likeA rowing boat. The rowers face backward. The cox sees the finish and calls the rhythm, but doesn't row.

    If the brain only shouted orders, nobody would need it. So the brain gets information the body doesn't have.

    CHAPTER 6

    The ragdoll (Rapier)

    In one lineThe human is 13 solid pieces joined by hinges. Motors in some hinges turn the pieces, and gravity does the rest.
    🪆

    Think of it likeAn action figure with small motors in the hips and shoulders. Gravity and the floor decide if it walks or falls.

    The physics engine is Rapier, written in Rust and compiled to WebAssembly, so it runs on the server in JavaScript. The world is 2D, side view, with gravity −9.81 m/s² and a fixed 1/60 s step.

    The body is a ragdoll: 13 rigid bodies (about 69 kg in total) connected by 12 revolute joints. Every joint has limits, so a knee can never bend backwards even when everyone does everything wrong. Collision groups stop the body from hitting itself: in 2D the left and right legs overlap.

    PartPlayers control
    LegsThe hip motor. The knee lifts by itself while the leg swings forward.
    ArmsThe shoulder motor. The elbow holds a slight bend.
    TorsoA lean torque on the torso.
    HeadNobody. It takes the hits.
    JointLimits
    Hip−0.8 to +1.7 rad
    Knee−2.3 to 0 rad (one way)
    Shoulder±3.1 rad
    Elbow0 to 2.4 rad
    Spine · neck±0.5 rad

    Motors

    Players drive position motors, not raw forces. The group average sets where the hip should point (mean × 1.0 rad), and a force-based motor moves it there: stiffness 8000, damping 400, max force 4000. The target moves at most 6 rad/s, so a group flipping direction can't snap the leg. Zero input means straight legs, so random noise averages out to standing still.

    Why 2D? Cheaper to run, faster to build, and a flailing 2D body is already funny. 3D can come later.

    CHAPTER 7

    Walking and balance

    In one lineThere is no walk button. Walking happens when the two leg groups take turns and the torso keeps balance.
    🚲

    Think of it likeTraining wheels. The balance assist stops a fall every second, but you still have to pedal in rhythm.

    A foot planted on the floor, with its leg swinging back, pushes the body forward. Then the legs swap. The knee bends only while its hip is swinging forward, so the moving foot clears the floor.

    If both legs push forward together, the human falls on its back. The brain's LEFT LEG NOW / RIGHT LEG NOW orders set the rhythm. That is why the game needs a brain.

    Balance assist

    A real ragdoll can't stand. So every tick the server adds a hidden torque that turns the torso and pelvis back toward upright:

    torque = −angle × 1000 − angularVelocity × 150     // applied to torso and pelvis

    Why 1000? The body is about 69 kg with its weight about 1 m up, so gravity tips it with roughly m·g·h ≈ 680 N·m per radian of lean. Any assist below about 700 can never hold it up.

    Too lowImpossible. Players give up.
    Middle · targetIt wobbles and stumbles, but a team that works together can walk.
    Too highIt never falls, so nothing is funny.
    CHAPTER 8

    Falls, the chair, death

    In one lineAfter each physics step, the server checks simple rules about where the body really is.
    📏

    Think of it likeA gymnastics judge: they don't move the gymnast, they only watch positions and decide.

    There are no canned animations. Sitting is not a "sit" animation: the players have to get the body onto the chair, and the server checks that it's there.

    Fall and get up

    Torso leaning more than ~70° for 1.5 s = it has fallen. Players hold Space; the shared bar fills by how many hold it (over 30% fills it). When full, the body is stood back up. If it fell beside the chair, it stands up 0.6 m before it, so it doesn't overlap the chair.

    Sit on the chair

    Pelvis on the seat of the chair, torso within ~25° of upright, both for 2 s. The time is compared with the record, and a new record is saved immediately.

    Damage

    If the head reaches the floor while moving faster than 3 m/s, health drops. The harder the hit, the bigger the drop.

    The human dies

    At 0 health the life is saved (how long it lasted, the cause, how many times it sat down). After 5 s a new life starts at the start line, and everyone's input is reset to 0.

    CHAPTER 9

    The tick loop

    In one line60 times a second the server reads the wishes, moves the body a little, checks the rules and tells everyone.
    🎞️

    Think of it likeFilm frames. The server makes 60 "frames" of the world each second. Each one is a tick.

    Every tick runs the same steps in the same order. Physics needs equal steps to stay stable; variable steps make joints jitter and explode when the server hiccups. Not everything needs 60 Hz though, so sending is spread out:

    every tick (1/60 s):
  1. drop players who went quiet
  2. average inputs per body part          (chapter 4)
  3. set the joint motors                  (chapter 6)
  4. step the physics
  5. check fall, damage, death             (chapter 8)
  6. check the chair                       (chapter 8)
  every 3rd tick:   send body positions    (20 Hz)
  every 30th tick:  send game info         (2 Hz)
  every 600th tick: save lives and records (every 10 s)
    One full tick (13 bodies, 12 joints, all the rules) takes about 0.047 ms, under 0.3% of the 16.7 ms budget. Physics is not the bottleneck. Sending data is.
    CHAPTER 10

    Time and smoothness

    In one lineThree clocks keep it fair and smooth: the loop timer, game time, and the browser's drawing time.
    📒

    Think of it likeA flipbook where only every third page is drawn. Your browser draws the pages in between.

    1 · Loop timer

    A timer fires every ~8 ms. An accumulator collects real elapsed time and runs as many 16.7 ms ticks as fit. A late timer runs two ticks; after a big freeze it runs at most five and drops the rest instead of fast-forwarding.

    2 · Game time

    Each tick adds exactly 16.67 ms. Every rule uses it: 60 s part swap, 2 s brain vote, 2 s chair check, 1.5 s fall check, 5 s between lives, 0.5 s input freshness, survival time. If the server lags, the game slows evenly and no rule is skipped.

    3 · Drawing time

    Positions arrive 20 times a second, which looks choppy if drawn directly. The browser draws the body 100 ms in the past, where it always has an update before and after, and blends between them. Angles blend the short way round (179° to −179° turns 2°, not 358°). The result is smooth 60 fps motion. 100 ms of delay would hurt a shooter; here, 8 people share one leg and nobody notices.

    What the server sends

    Snapshot · about 292 bytes of JSON · 20 per second

    tick + for each of 13 pieces: x, y, angle (rounded to 3 decimals) + each group's average + get-up bar

    // game info · JSON · 2 per second
{ "t": "meta", "players": 12, "queue": 0, "watching": 30,
  "brain": { "cmd": "WALK_RIGHT", "votes": 1, "of": 2 },
  "emotes": { "GO": 4 }, "life": 7, "health": 82,
  "objective": { "name": "REACH THE SEAT", "ms": 48210 },
  "roster": [...]   // only when someone joins, leaves or is reassigned
}

    The player list used to be resent twice a second and made up over 40% of all the data sent. Now it goes out only when it changes. Switching to binary was considered and measured: it would save only about 35%, because the JSON is already small.

    CHAPTER 11

    Architecture and data

    In one lineOne Cloudflare Durable Object is the one human: it holds every connection, runs the loop, and stores the records.
    🗳️

    Think of it likeOne referee for the whole world. Cloudflare guarantees there is only ever one.

    Normal multiplayer games split players across many servers. This one can't: two servers would mean two humans. So it needs a guarantee that exactly one copy of the game runs. Cloudflare Durable Objects give that: idFromName("one-human") returns the same single object from anywhere in the world.

    DataWhere it livesWhy
    Body positions, inputs, seats, votesDurable Object memoryChanges 60 times a second. Not worth saving.
    Life number, record, last 50 livesDurable Object storage (SQLite)Survives restarts and deploys. A few KB.
    Anything per browserNothingNo accounts, no cookies.

    No Redis, no Postgres. The first plan had Redis for live state and crash backups, and Postgres for history. One Durable Object has its own memory and storage, and since there is only one, there is nothing to sync between servers. The history is tiny, so a database server would be overkill. When leaderboards and replays arrive, they can go in SQL tables in the same object or in Cloudflare D1.

    Same code on a laptop. The game is one plain TypeScript class that doesn't know where it runs. Locally it's wrapped by a Node server with a JSON file for storage; on Cloudflare by the Durable Object.

    Costs nothing when empty. The loop starts when the first person connects and stops when the last one leaves.

    One catch: Cloudflare Workers can't compile WebAssembly from bytes at runtime, and Rapier ships its WASM as a base64 string inside its JavaScript. A build script rewrites Rapier's loader to use a precompiled .wasm file instead.

    Scaling plan. Each player receives roughly 6 KB/s. When one object can't fan out to everyone, gateway objects will hold the sockets and send the main object only a sum and a count per group. An average can be built from partial sums, so the result is identical.
    CHAPTER 12

    What broke along the way

    In one lineThe ragdoll failed five different ways before it could walk.
    1. It melted into a crouch.With the default motor model the joints were too weak to hold the body's weight. Switching to force-based motors made it stand, and then tip over like a statue.
    2. The statue fell.The balance assist was 520, below the ~680 N·m per radian gravity applies. Raised to 1000.
    3. It did a headstand.The assist only pushed the torso, so the pelvis tipped and the body flipped. Now it pushes both, and wraps angles with atan2 so a body near 180° isn't pushed the wrong way.
    4. It did the splits.Holding a key kept moving the hip further, so small random input piled up. Now the group average sets the angle directly.
    5. It walked backward.The knee bent based on where the hip pointed. Bending it only while the hip swings forward made it walk forward: 4.5 m in 20 s.
    6. Cloudflare refused the physics engine.Runtime WebAssembly compilation is blocked. Fixed with the build step from chapter 11. The first version broke on a stray .buffer left by a regex.

    Questions people ask

    Can trolls ruin it?

    They can slow it down, not take over. Each limb uses the average, so 30% trolls only make it weaker. Calls count once per person, and everyone is reassigned every 60 seconds.

    Why not let each browser run its own physics?

    There would be thousands of slightly different humans, and cheaters could teleport the body. One server with the only copy keeps everyone in the same world.

    Can a late message from the last life move the new one?

    No. WebSockets keep messages in order, each input replaces the last, anything older than 0.5 s is ignored, inputs carry the life number, and everyone's input is reset when a new life starts.

    Isn't there lag?

    About 0.1–0.2 s. It doesn't matter when 8 people share one leg.

    What happens when every seat is taken?

    You wait in line and watch. When someone leaves, the first person in line gets their seat.
